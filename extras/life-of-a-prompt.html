Life of a Prompt

What happens, and where, between pressing Enter and seeing the answer. The indigo line is your request. It goes down through the provider's servers to the GPUs, loops once for every token of the answer, and comes back up to you.

Step by step, with one question

Tap or click a box in the diagram to jump to its step. The example uses a real open model, Qwen2.5-32B-Instruct, so the token numbers are real.

On your phone or laptop

  1. 1

    You press Enter

    The app sends your message to the provider's servers as plain text, over an encrypted connection. Nothing AI happens on your phone: no tokens, no model.

    What's the capital of Australia?

The harness, on the way in

Ordinary servers in the provider's data center, no GPUs.

  1. 2

    Front door

    Checks who you are and whether you're within your limits, then hands the request to a model server that has the model loaded. Some apps also decide here which model should answer.

  2. 3

    Safety check

    Many providers run your message past a small, separate model trained to spot harmful requests. It only gives a verdict. It doesn't write anything.

  3. 4

    Build context

    Gathers everything the model will read this turn: the hidden system prompt, the whole chat so far, saved memories about you, descriptions of the tools it may use, and your new message. If that's more than the context window holds, the oldest parts are dropped or summarized.

  4. 5

    Chat template

    Stitches it all into one long text, with special markers for who said what. It ends on the assistant's marker, so the most natural way to continue the text is a reply. The model only ever continues text.

    <|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
What's the capital of Australia?<|im_end|>
<|im_start|>assistant

    Qwen's markers. Each model family has its own. If you give no system prompt, this template adds one anyway: “You are Qwen, created by Alibaba Cloud. You are a helpful assistant.”

The model server

A machine with several GPUs. Only steps 7 to 9 are the trained network, the LLM itself. The tokenizer, sampler and detokenizer are plain code around it.

  1. 6

    Tokenizer

    Runs on the server's ordinary processor. It cuts the text into word pieces and swaps each piece for its number in the vocabulary. Each marker is a single token of its own. The whole prompt above becomes 26 tokens.

    What3838 's594 ·the279 ·capital6722 ·of315 ·Australia8330 ?30

    Your question is 7 of those tokens. A dot marks a space, which belongs to the next word's piece. The marker <|im_start|> is token 151644.

  2. 7

    Embedding layer

    The LLM's first layer. It's a table with a row for every token, about 152,000 rows. Each token number picks its row: a list of 5,120 numbers (12,288 in GPT-3). That list is the token's notepad. Its position in the text gets marked too.

  3. 8

    Transformer layers

    The notepads go up the tower: 64 layers here, 96 in GPT-3. In each layer, attention lets the tokens compare notes, and the feed-forward part lets each token think on its own. Every layer adds what it found to the notepads.

    Each layer also keeps the keys and values it worked out for every token so far, in GPU memory. That's the KV cache. On later trips, only the newest token needs working out; the earlier ones are looked up.

  4. 9

    Output layer

    Holds the last token's notepad up against every token in the vocabulary, gives each a score, and turns the scores into probabilities: the spread of bets.

    The 62% Canberra 31% Australia 4% …

    Made-up numbers, for illustration.

  5. 10

    Sampler

    A few lines of plain code. Nothing in it is trained. It rolls weighted dice over the bets. Temperature makes it bolder or safer, and top-p cuts off the long tail of unlikely tokens.

    picks “The”, token 785

  6. ↺

    Around again, once per token

    The picked token number goes straight back into the embedding layer, skipping the tokenizer, and the next trip starts. The first trip read all 26 prompt tokens at once, in parallel: that's the pause before the first word. After that it's one trip per token, which is the speed you watch the text appear. It stops when the sampler picks the end marker.

    The785 ·capital6722 ·of315 ·Australia8330 ·is374 ·Canberra68790 .13 <|im_end|>151645

    Seven tokens plus the end marker: eight trips up the tower.

  7. 11

    Detokenizer

    The tokenizer in reverse. Each picked number becomes its piece of text and is sent on right away. That's why answers appear piece by piece.

    785 → "The" 6722 → " capital" …

The harness, on the way out

  1. 12

    Tool call?

    Sometimes the model writes a request for a tool instead of an answer: search the web, run some code, look in your files. The harness runs the tool, adds the result to the context (step 4), and sends everything through the model again. The model never touches the internet itself. It only writes the request.

  2. 13

    Safety check

    Often a safety model also reads the answer as it streams, and can stop it.

  3. 14

    Send and save

    Streams the text to your app as it's made, and saves the chat. Next turn, all of it goes through every step again, because the model rereads the whole conversation each time.

Back on your phone or laptop

  1. 15

    The answer appears

    The app shows the text and turns the model's markdown into formatting. Asterisks become bold, pound signs become headings, and pipes become tables.

Two things called “embedding”

In a plain chat there's no separate embedding model. The embedding is the LLM's own first layer (step 7). An embedding model joins in only when something gets searched, such as your files or a company's documents.

The vector database holds a list of numbers for every passage of your files, made in advance by the same embedding model. This is called RAG, retrieval-augmented generation. The LLM then reads the passages it was handed like any other text.

Also good to know

Many chats share each trip

The GPUs work on many people's requests in the same pass. That's called batching, and it's how one machine serves many chats at once.

Big models are split up

A model too big for one GPU is spread across several, often 8 in one machine, and they work on every trip together. The biggest models span several machines.

Rereading costs less than it sounds

Providers keep the KV cache for the start of a conversation for a few minutes. That's prompt caching: the part that hasn't changed isn't worked out again, so the next turn starts faster and costs less.

Thinking models use the same loop

A reasoning model first writes its working notes as ordinary tokens, then the answer. Qwen3 puts them between <think> and </think>. Apps usually hide or summarize the notes, but every one is a trip up the tower.

Pictures get their own encoder

An attached image is cut into small patches, and a vision encoder turns each patch into a list of numbers. Those join the token notepads at step 7.

The harness can run on your side

Use a model through its API and your own program does steps 4 and 14: it builds the context and sends the whole chat every time. An agent like Claude Code is a harness on your computer, or in a cloud container like the one that makes this podcast. It reads files, runs tools and calls the model's servers in a loop.

The example model is Qwen2.5-32B-Instruct, an open-weight chat model whose tokenizer, chat format and size are public. The token numbers and counts come from its real tokenizer; the percentages in step 9 are made up.

ChatGPT, Claude and other assistants follow the same outline. Their companies don't publish the exact parts.
